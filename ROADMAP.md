# AutoZapret — ROADMAP

> **Что это.** Один Windows-инструмент «всё-в-одном» для обхода DPI: GUI-обёртка над
> `winws.exe` (zapret 1 и zapret 2) + встроенный Telegram WS-прокси + менеджер списков
> и фейк-payload'ов. Сворачивается в трей, умеет автоподбор стратегии, обновляется сам.
>
> **Стек.** C# / **.NET 9** (`net9.0-windows`) / **WebView2** (UI — HTML+CSS+JS, общение через
> `chrome.webview.postMessage`), x64, WinForms-хост, `NotifyIcon` для трея.
> Публикация — self-contained single-file: .NET у пользователя не нужен.
>
> **Референс по форме проекта:** `../NFSWorldServer2` — тот же подход: UI в ресурсах,
> `refs/` в `.gitignore`, `--selftest`.
>
> Дата: 2026-11-04. Исследование источников: `docs/research/*.md`.

## 0. TL;DR

| | |
|---|---|
| **Проблема** | Все существующие обвязки над zapret — это либо `.bat`-файлы (Flowseal), либо WPF-монолит на .NET 10 (FluxRoute), либо bash для роутеров (Zapret-Manager). Для обычного пользователя Windows нет нормального GUI с треем, автоподбором и Telegram-прокси в одном окне. |
| **Решение** | `AutoZapret.exe` — один x64-бинарь на .NET 4.8 (работает даже там, где .NET 5+ не поставить), UI на WebView2, движок zapret рядом в `engine/`, прокси внутри процесса. |
| **Ключевая идея** | **Стратегии — это данные, а не код.** 22 стратегии Flowseal + 64 стратегии Zapret-Manager + автогенерируемые = один `strategies.json`. Движок (`winws`/`winws2`) — сменный. |
| **Главный технический трюк** | Запускать `winws.exe` **напрямую** с массивом аргументов (не через `.bat`), чтобы владеть процессом, PID-деревом и кодом выхода. Разбор `.bat` — только как импорт. |
| **Главная юридическая мина** | FluxRoute под **GPL-3.0** — код копировать нельзя, только идеи. zapret/zapret2/Flowseal — MIT, WinDivert — LGPLv3/GPLv2 (см. §3). |

## 1. Жёсткие рамки (не обсуждается без причины)

1. **.NET 9** (`net9.0-windows`), x64. Миграция с .NET Framework 4.8 сделана в 0.2.0.
   **Windows 7 и 8.1 больше не поддерживаются** — .NET 9 требует Windows 10 1607+.
2. **Никакого NuGet, никаких пакетов.** Только BCL + WebView2 SDK (managed DLL из
   `lib/webview2`, как в NFSWorld2). Сборка — `build.cmd`, публикация — `publish.cmd`
   (self-contained single-file, .NET у пользователя не нужен).
3. **x64 обязателен.** `WinDivert64.sys` — единственный драйвер в бандле, 32-битной сборки
   `winws.exe` нет. Проверять `Environment.Is64BitProcess` на старте.
4. **UI — WebView2, не WinForms-контролы.** Форма — только хост и трей. Вся вёрстка в
   `web/` (`ui.html`, `app.js`, `theme.css`), вшитая ресурсами.
5. **Мост — `chrome.webview.postMessage`**, без `window.external` и без COM-скриптинга
   (в NFSWorld2 это отдельно отмечено как выстраданное решение).
6. **Данные вместо кода.** Новая стратегия = запись в JSON, а не `if (name == "ALT7")`.
7. **Никаких секретов и приватных данных в логах и на публичных экранах.**
8. **`refs/`, `engine/`, `bin/`, `data/state/` не попадают в git.**

## 3. Лицензии — решить до первой строки кода

### 3.1 Можно

- **Шипить** `winws.exe`, `winws2.exe`, `lua/`, `.bin`-фейки, конфиги Flowseal — всё MIT,
  достаточно приложить тексты лицензий и ссылки на апстримы.
- **Портировать `tg-ws-proxy`** на C# — MIT, с сохранением attribution.
- **Переосмыслять идеи FluxRoute** — идеи не охраняются.

### 3.2 Нельзя

- **Копировать код FluxRoute.** GPL-3.0 заразна: производный продукт обязан быть GPL.
  Если AutoZapret не GPL — из FluxRoute берём только **подходы**, не строки и не структуру
  файлов «один-в-один».
- **Модифицировать WinDivert** и шипить модифицированный бинарь. LGPLv3 требует
  возможности замены — значит `WinDivert.dll` и `WinDivert64.sys` лежат **отдельными
  файлами рядом с exe**, а не внутри ресурсов.

### 3.3 Обязательный минимум

- [x] `licenses/zapret-MIT.txt`, `licenses/flowseal-MIT.txt`, `licenses/WinDivert-LGPLv3.txt`,
      `licenses/tg-ws-proxy-MIT.txt` — **скачаны и лежат в репозитории**.
- [x] Экран «О программе»: версия приложения, ОС, права, режим данных, WebView2,
      каталог данных; таблица компонентов с лицензиями (MIT / LGPLv3).
- [x] README: «это не VPN», «WinDivert может флагаться AV», «используйте на свой риск»,
      раздел про SmartScreen и исключение Defender.

### 3.4 `TLSpack` и `_Add1` — вопрос закрыт (2026-11-04)

**`refs/TLSpack` = [HatabaSS/zapret-custom-binaries](https://github.com/HatabaSS/zapret-custom-binaries), MIT.**

Проверено побайтово: структура совпадает полностью (1672 файла, те же каталоги),
а `steam/tls_clienthello_steampowered_com_20260205T122407.bin` имеет
**идентичный SHA-256** в апстриме и у нас (`6F67D481…B22F0FDA`, 517 байт).

Следствие: **`TLSpack` можно шипить** в составе AutoZapret. Достаточно положить
`licenses/zapret-custom-binaries-MIT.txt` и ссылку на апстрим.
Это снимает ограничение «только локальный кэш» из прошлой версии этого раздела.

**`_Add1` (`payloadGen` v0.8) — автор StressOzz, лицензия НЕ указана.**

Установлено по [issue #34 Zapret-Manager](https://github.com/StressOzz/Zapret-Manager/issues/34#issuecomment-3641163824):
StressOzz выложил `payloadGen_v0.8.zip` (2025-12-11), версия совпадает с нашим исходником.
У `Zapret-Manager` нет файла LICENSE и нет упоминаний лицензии в readme
→ действует «все права сохранены».

Следствие: **шипить `payloadGen.exe` или его исходник нельзя.** Изучать логику и писать
свой генератор по мотивам — можно (идеи не охраняются).

### 3.5 Что делать с Zapret-Manager

`Zapret-Manager` (StressOzz, 2.1k звёзд) — **без файла лицензии**. Мы брали оттуда
**каталог стратегий** (v1-v10, Yv01-Yv33, Dv1-Dv17, Gv1-Gv4) как справочник и
переосмыслили в своей модели данных. Сами аргументы `winws` — это факты о протоколе,
а не творческая работа, но:

- **не копировать** bash-код `Zapret-Manager.sh` (2100+ строк) целиком;
- если понадобится именно код — сначала спросить автора (issue в его репозитории);
- наш `strategies.json` собран из **Flowseal** (MIT) — это основной источник, Zapret-Manager
  использовался для сверки и идей.

### 4.1 Один exe, слои внутри

```
AutoZapret.exe  (x64, WinExe)
│
├── App/            хост: MainForm (WebView2), TrayController, WebBridge, SingleInstance
├── Core/           Json, Log, Settings, Paths, AtomicFile, Result<T>
├── Zapret/         EngineLocator, StrategyStore, WinwsLauncher, WinwsSupervisor,
│                   ServiceManager, GameFilter, WinDivertControl
├── Lists/          HostlistManager, IpsetManager, ListUpdater, HostsFile
├── Payloads/       PayloadLibrary, PayloadValidator
├── Diag/           Diagnostics, ConnectivityProbe, Scoring
├── Update/         EngineUpdater, SelfUpdater
├── Proxy/          TgProxyServer, TgProtocol, AesCtr, WsServer, WsClient, FakeTls, DcTable
└── Orchestrator/   ProbeLoop, Bandit, Evolver, NetworkFingerprint
```

Сборка — `dotnet build` (список `.cs` задан в csproj), UI-ассеты — `EmbeddedResource`.
Публикация — `dotnet publish` self-contained single-file.

### 4.2 Раскладка репозитория

```
AutoZapret/

├── ROADMAP.md           ← вы здесь
├── AGENTS.md            правила для агентов и людей
├── README.md            для пользователя
├── build.cmd            сборка без MSBuild
├── run.cmd
├── .gitignore
├── docs/
│   └── research/        5 разборов источников
├── src/AutoZapret/      *.cs
├── web/                 ui.html, app.js, theme.css
├── assets/
│   ├── AutoZapret.ico
│   ├── strategies/      strategies.v1.json, strategies.v2.json
│   ├── lists/           дефолтные hostlist/ipset (маленькие, шипятся)
│   └── fakes/           отобранные .bin + fakes.json
├── lib/webview2/        SDK, качается tools\fetch-webview2.ps1
```

### 4.3 Правила слоёв

- `App/` знает про всё; `Core/`, `Zapret/`, `Lists/` — **не знают** про UI.
- UI общается с ядром **только** через `WebBridge` (один вход — `OnWebMessage`, один выход — `Send(json)`).
- Долгие операции — в `ThreadPool`, ответ — сообщением в страницу. UI-поток не блокировать.
- Любой фоновый цикл — с `CancellationToken` и явным `Stop()`, чтобы приложение закрывалось мгновенно.

## 5. Модель данных

### 5.1 Стратегии — JSON, аргументы — массив токенов

Принципиально: **`args` — это массив**, а не строка. Никакой склейки и повторного разбора
кавычек (в FluxRoute это отдельно отмечено как единственно верный путь — `ArgumentList`).

```json
{
  "schema": 1,
  "engine": "v1",
  "source": { "repo": "Flowseal/zapret-discord-youtube", "version": "1.10.4", "importedAt": "2026-11-04" },
  "strategies": [
    {
      "id": "flowseal.general",
      "name": "general",
      "engine": "v1",
      "targets": ["discord", "youtube"],
      "rating": { "note": "универсал: multisplit + seqovl", "recommended": true },
      "profiles": [
        {
          "name": "QUIC",
          "label": "UDP 443 (QUIC)",
          "filter": { "udp": "443", "hostlist": ["list-general", "list-general-user"] },
          "args": [
            "--filter-udp=443",
            "--hostlist=${LISTS}/list-general.txt",
            "--hostlist=${LISTS}/list-general-user.txt",
            "--hostlist-exclude=${LISTS}/list-exclude.txt",
            "--ipset-exclude=${LISTS}/ipset-exclude.txt",
            "--dpi-desync=fake",
            "--dpi-desync-repeats=6",
            "--dpi-desync-fake-quic=${BIN}/quic_initial_www_google_com.bin"
          ]
        }
      ]
    }
  ]
}
```

**Плейсхолдеры** (подставляются в рантайме, всегда абсолютными путями):

| Плейсхолдер | Значение |
|---|---|
| `${BIN}` | `<app>/engine/bin` |
| `${LISTS}` | `<app>/engine/lists` |
| `${FAKES}` | `<app>/assets/fakes` |
| `${GAME_TCP}` / `${GAME_UDP}` | порты из `game_filter.enabled` (`1024-65535` или `12`) |
| `${WF_TCP}` / `${WF_UDP}` | базовые порты перехвата (`80,443,2053,...`) |

Глобальные аргументы (`--wf-tcp=`, `--wf-udp=`, `--new`-разделители) собираются
`WinwsLauncher` из профилей — их не дублируем в каждом профиле.

### 5.2 Настройки

`data/state/settings.json` — атомарная запись (`temp` → `File.Replace` → `.bak`), при битом
файле — `*.corrupt-<ts>` и дефолты (это выстраданное решение FluxRoute, повторяем).

```json
{
  "schema": 1,
  "engine": { "kind": "v1", "path": "engine", "version": "1.10.4" },
  "zapret": {
    "strategyId": "flowseal.general",
    "gameFilter": "tcp+udp",
    "ipsetMode": "loaded",
    "autoStart": true,
    "serviceMode": false
  },
  "proxy": { "enabled": false, "host": "127.0.0.1", "port": 1443, "secret": "dd…", "cfProxy": true },
  "ui": { "theme": "dark", "simpleMode": true, "minimizeToTray": true, "startMinimized": false },
  "updates": { "engine": true, "app": true, "lists": true, "channel": "stable" }
}
```

### 5.3 Списки

| Файл | Роль | Источник | Шипим? |
|---|---|---|---|
| `list-general.txt` | домены-цели | Flowseal | да |
| `list-general-user.txt` | цели пользователя; `!domain` = исключение | UI | создаётся |
| `list-exclude.txt` | исключения | Flowseal + `exclude-domains.txt` V3nilla (27 доменов) | да |
| `list-exclude-user.txt` | исключения пользователя | UI | создаётся |
| `list-google.txt` | YouTube/Google | Flowseal | да |
| `ipset-all.txt` | CIDR-цели | V3nilla (33 336 записей, **CRLF → нормализовать**) | качать |
| `ipset-exclude.txt` | CIDR-исключения | V3nilla `exclude.txt` (6 записей) | да |
| `list-youtube.txt` | доп. YouTube | zapret-win-bundle | да |

⚠️ Синхронизация пользовательских списков — **идемпотентная**: сравнивать множество
доменов и не перезаписывать файл, если набор тот же (иначе каждый старт затирает
комментарии пользователя — issue #77 у FluxRoute).

**Найдено при проверке (важно):**
`kws*.web.telegram.org` **блокируется на уровне TCP** — не TLS, не SNI, а сам коннект.
Ни одна из 22 desync-стратегий его не пробивает, и это согласуется с тем, что
`web.telegram.org` не проходил ни в одном тесте. Значит:
  * прокси технически готов и корректен (handshake проходит в selftest);
  * но в этой сети он не заработает без внешнего туннеля;
  * Cloudflare-фронты из `tg-ws-proxy` сейчас отдают 404 на `/apiws` и 501 на `/api`
    (проверены все 20 доменов) — похоже, публичный пул мёртв, нужен свой домен
    или Worker (см. `docs/research/tg-ws-proxy.md` §2.5, варианты C и D).

#### Транспорты: что реально может пробить (записано 2026-11-05)

Живой лог подтвердил блокировку адресом:

```
15:00:23.486 PROXY не удалось подключиться к Telegram: kws2.web.telegram.org: таймаут TCP
... семь одинаковых строк за восемь секунд
```

И там же нашёлся **наш собственный баг**: для обычного (не медиа) подключения
`DcTable.WsDomains` отдавал **один** домен, без резерва. То есть в этой сети
пробовать было нечего вовсе. Исправлено: теперь всегда два (`kwsN` и `kwsN-1`).

Но два имени — это не «пробить», это «перебрать». Настоящих путей ровно четыре,
и они разной степени готовности:

| Транспорт | Что нужно | Готовность | Честная оценка |
|---|---|---|---|
| **Прямой WS** (`kwsN.web.telegram.org`) | ничего | ✅ работает | не работает там, где адрес режется. У нас именно так |
| **Cloudflare Worker** (свой домен `*.workers.dev`) | аккаунт CF, 5 минут | 🟡 код готов, ждёт рабочий воркер | **самый дешёвый реальный путь.** Транспорт в программе готов: `WsTunnel` + поле «Внешний релей» + кнопки «Проверить» и «Как сделать свой?». Воркер заказчика пока отвечает 426 на `?probe=`, то есть на нём ещё старый код |
| **CF-прокси на своём домене** | купленный домен в CF | ⬜ позже | работает, но нужен домен; публичный пул из 20 `.co.uk` мёртв (404 на `/apiws`) |
| **Свой VPS / WARP** | сервер или WARP-клиент | ⬜ дорого | самый надёжный и самый дорогой: это уже P11 (туннель), а не прокси |

**Почему Worker — правильный следующий шаг.** Он не требует ни домена, ни сервера,
и его код уже написан чужой рукой (MIT, `tg-ws-proxy`). Механика простая:

```
мы  →  wss://<worker>.workers.dev/apiws?dst=kws2.web.telegram.org
     →  Worker: connect({hostname: dst, port: 443})
     →  Telegram: наш HTTP-Upgrade, потом WS-кадры
```

То есть Worker — это «розетка»: он открывает TCP туда, куда мы скажем, и
перекладывает байты. Всё шифрование и MTProto остаются нашими.

**Что нужно от заказчика, чтобы это заработало:** завести Worker по инструкции
из `refs/tg-ws-proxy/docs/RU/CfWorker.md` и дать его домен
(`random-words-1234.username.workers.dev`). Дальше — поле в настройках
и домен в списке маршрутов **первым**.

**Чего НЕ делаем и почему:** подмену SNI по IP (это работает для Bot API, но не
для WS — проверено, `tools/tg-front-probe.js`), и «свой WARP» внутри прокси —
это отдельный туннель, то есть P11, а не правка прокси.

### P8 — Оркестратор (то, что FluxRoute называет «ИИ») `[x]`

- [x] `AutoPilot` — цикл раз в 20 минут: проверить → записать → после **2 неудач подряд**

- [x] Отпечаток сети (`NetworkFingerprint`) — при смене сети статистика берётся заново.
- [x] Автопилот живёт только вместе с запущенным обходом; при остановке гаснет сам.
- [x] Смена стратегии автопилотом сохраняется в настройки (иначе после перезапуска вернётся старая).
- [x] UI: тумблер в настройках, живой статус (состояние, счёт, следующая проверка).

### P10 — СВОЙ АНАЛОГ ZAPRET `[ ]` ⭐ задача со звёздочкой, самый конец

> Это «попробуем», а не обещание. Делается **только после** того, как P0-P9 закрыты и
> продукт живёт. Смысл: перестать зависеть от `winws.exe` (cygwin-бинарь под MIT,
> но чужой) и получить полностью свой движок — с сохранением совместимости с его конфигами.

**Почему это вообще возможно.** `winws.exe` — это `nfqws` для Windows: перехват через
WinDivert + модификация пакетов. Вся «магия» — не в перехвате, а в **наборе desync-техник**,
которые описаны в `lua/zapret-antidpi.lua` (27 функций) и в help-тексте exe (113 опций).
Перехват WinDivert доступен из C# через P/Invoke (`WinDivertOpen/Recv/Send/Close`) —
`WinDivert.dll` даёт плоский C API, никакого cygwin не нужно.

> **Решение по движкам (2026-11-04, требование владельца):**
> свой движок **не заменяет** zapret 1/2, а добавляется третьим вариантом.
> `winws` и `winws2` остаются **навсегда** как fallback: они проверены на живых
> провайдерах, а свой движок по определению моложе и может не покрывать редкие DPI.
> Выбор движка — в интерфейсе (`EngineKind { Zapret1, Zapret2, Builtin }`, позже
> `+ Mihomo, Xray`), с явной пометкой, что «встроенный» — экспериментальный.
> Автопилот и пресеты должны уметь переключаться между движками, а не только
> между стратегиями одного движка.

#### Этапы

- [~] **P10.1 — WinDivert-слой на C#.**
      Сделано (фундамент, без риска для сети):
      `WinDivertInterop` — P/Invoke `Open/Recv/Send/Close/SetParam`, флаги
      `SNIFF/DROP/RECV_ONLY/…`, `WINDIVERT_ADDRESS` читается по смещениям
      (битовые поля в C#-структуре дают мусор молча). Резолвер DLL: `WinDivert.dll`
      лежит в `engine\bin`, обычный поиск её не находит, а рядом с ней драйвер.
      `--netcap [сек]` — сниффер TCP/443 **в режиме SNIFF**: пакеты копируются,
      но не задерживаются, поэтому первый слой в принципе не может сломать сеть.
      Считает пакеты, разбирает IPv4/IPv6+TCP/UDP и достаёт SNI из ClientHello.
      selftest: 14 проверок разбора на синтетических пакетах (смещения, порты,
      IPv6, UDP, мусор) — и они сразу поймали ошибку в моём же построителе
      IPv4-заголовка.
      Осталось: реинжект через `WinDivertSend` и `WinDivertHelperCalcChecksums`,
      затем очередь и модификация. Цель этапа — «перехватить TCP/443 и вернуть
      байт-в-байт» — пока не достигнута.
- [~] **P10.2 — Разбор пакетов.** IPv4/IPv6, TCP/UDP, смещения и полезная
      нагрузка уже есть (`PacketParser`), определение L7 по первым байтам —
      частично: TLS ClientHello распознаётся и SNI извлекается. Не сделано:
      seq/ack/flags/options/timestamps, `http_req`, `quic_initial`, `stun`,
      `discord_ip_discovery`.
- [~] **P10.3 — Desync-техники, порт с lua.** По одной, с тестом на каждом шаге:

### P11 — Mihomo / Xray: полноценный VPN `[ ]` ⭐ задача со звёздочкой, самый конец

> Смысл: AutoZapret перестаёт быть «только обходом DPI» и становится комбайном
> в духе **Hiddify** и **Happ** — один интерфейс, несколько движков, каждый для своей задачи.
> Делается **после** P10, когда свой движок уже есть.

**Зачем это вообще нужно рядом с zapret.** Обход DPI не спасает, когда:
- блокировка по IP (zapret прямо об этом пишет: «не VPN и не помогает при блокировке по IP»);
- нужен выход в другой стране (стриминг, региональные сервисы);
- провайдер режет по SNI целиком, и подделка hello уже не проходит;
- нужен стабильный туннель для конкретного приложения, а не «всё подряд».

Тогда нужен именно прокси/VPN, а не desync. Комбайн даёт выбор: **desync там, где он
работает (быстро, без сервера), туннель там, где без него никак.**

#### P11.1 — Mihomo (Clash Meta)

- [ ] Скачивание и версионирование `mihomo.exe` (x64), проверка SHA-256.
- [ ] Генерация `config.yaml` из подписок: `proxies`, `proxy-groups`, `rules`,
      `dns` (DoH), `tun` (system proxy vs TUN).
- [ ] Подписки: загрузка по URL, парсинг base64-списка `vmess://`/`vless://`/`ss://`/`trojan://`,
      конвертация в формат Clash (`proxies:`), автообновление по расписанию.
- [ ] Управление: `external-controller` (REST API на 127.0.0.1:9090) — выбор узла,
      задержки, переключение группы, режим `rule`/`global`/`direct`.
- [ ] TUN-режим требует прав администратора и драйвера (wintun) — отдельный сценарий
      повышения прав, как у WinDivert.
- [ ] UI: список узлов с пингом, группы, «выбрать лучший по задержке».

#### P11.2 — Xray (v2ray-core)

- [ ] Скачивание `xray.exe`, проверка SHA-256.
- [ ] Генерация `config.json`: `inbounds` (socks/http), `outbounds` (vless/vmess/trojan/shadowsocks),
      `routing` (домены/IP → прямо или через прокси), `dns`.
- [ ] Поддержка `vless://` с `reality`, `xtls-rprx-vision`, `ws`, `grpc`, `httpupgrade` —
      это то, что чаще всего дают в подписках.
- [ ] Подписки: тот же загрузчик, что у Mihomo (общий слой `SubscriptionStore`).
- [ ] Гео-файлы `geoip.dat` / `geosite.dat` — скачивание и обновление.

#### P11.3 — Общая обвязка (делает комбайн комбайном)

- [ ] `RoutingPolicy` — **одна** таблица правил на все движки:
      «этот домен → через zapret», «этот → через Mihomo», «этот → напрямую»,
      «этот процесс → всегда туннель».
- [ ] `EngineKind { Zapret1, Zapret2, Builtin, Mihomo, Xray }` — единый интерфейс
      `IProtectionEngine { Start, Stop, Status, ApplyPolicy }`.
- [ ] Автовыбор движка: проба показала, что desync не помогает → предложить туннель.
      И наоборот: туннель не нужен, если desync справляется (экономия трафика и батареи).
- [ ] Один экран «Подключение»: тумблер, движок, профиль/узел, статус, скорость.
- [ ] Никаких конфликтов: одновременно активен **один** движок; переключение = стоп → старт.
- [ ] Импорт подписок из Hiddify/Happ/v2rayN (форматы `vless://`, `vmess://`, `clash://`).

#### Риски

- **Юридически:** Mihomo (GPL-3.0), Xray (MPL-2.0) — отдельные процессы, не линкуемся.
  Шипить можно, но тексты лицензий и source offer обязательны. GPL-3.0 у Mihomo —
  значит **нельзя** встраивать его код в наш exe, только запускать отдельным процессом.
- **Технически:** TUN-режим = драйвер + маршруты + DNS, и это конфликтует с WinDivert.
  Нужна аккуратность: пока активен туннель, zapret должен быть выключен.
- **Продуктово:** комбайн легко превращается в «настройки на 200 полей». Держать
  простой режим: одна кнопка + выбор «обход / туннель / напрямую».
- **Не блокирует релизы.** Это отдельная ветка продукта, не обязательство.

### P12 — Android-версия `[ ]` ⭐ задача со звёздочкой, САМОЕ ПОСЛЕДНЕЕ

> Ориентир: [romanvht/ByeByeDPI](https://github.com/romanvht/ByeByeDPI) — Kotlin, **GPL-3.0**,
> minSdk 21, 4 ABI, движок **byedpi** собран нативно через CMake, трафик заворачивается
> через `VpnService` + tun fd.

**Честная оценка «насколько легко»: приложение — средне, движок — это и есть вся работа.**

#### Что НЕ переносится вообще (и почему)

| Наш компонент | На Android | Почему |
|---|---|---|
| .NET Framework 4.8 | ❌ | Только .NET 8/9 (`net9.0-android`). Это не «сложно», это просто другая платформа: нужен полный переезд |
| WinForms | ❌ | Android UI — MAUI (XAML) или Blazor Hybrid. Переписывать все 6 экранов |
| WebView2 | ❌ | Это Edge/Chromium для Windows. На Android — `android.webkit.WebView`. Наш мост `chrome.webview.postMessage` **не работает**, нужен `IJSRuntime` (Blazor) или JS-bridge руками |
| **WinDivert** | ❌❌ | Драйвер ядра Windows. На Android перехват — это `VpnService` + tun fd, то есть **другой принцип целиком** |
| **winws.exe / winws2.exe** | ❌❌ | Windows PE + WinDivert. Не запустится никогда. Всё, что мы делали в P1/P7, на Android неприменимо |

#### Что переносится почти без изменений (~40% не-UI кода)

Если вынести это в отдельную библиотеку на .NET 9, она поедет в MAUI как есть:

- `Json`, `AtomicFile`, `Log`, `Settings` (модель + нормализация)
- `StrategyParser` / `StrategyStore` — **модель** стратегий (аргументы как массив токенов)
- `HostlistManager`, `ListsUpdater`, `HostsFile` (разбор, дедуп, IPv4/IPv6-логика, маркеры)
- `PayloadValidator` (проверка `.bin` — формат один и тот же)
- `ScoreStore`, `Bandit`, `WilsonLowerBound` — статистика и автоподбор **полностью переносимы**
- `BlockKind` / `DeepProbe` — классификация блокировок (сокеты есть везде)

#### Что придётся делать заново (это и есть цена)

1. **Движок desync.** Варианты:
   - **byedpi** (C, как в ByeByeDPI) через JNI + CMake — быстрее всего, но GPL-3.0;
   - **hev-socks5-tunnel** — другой принцип (SOCKS → tun), тоже нативно;
   - свой движок на C/Java поверх tun fd — самые большие трудозатраты.
2. **`VpnService` + tun fd** — вся маршрутизация, DNS, per-app split tunneling, foreground-сервис,
   уведомление, разрешение VPN (диалог системы). В ByeByeDPI это `ByeDpiVpnService.kt`.
3. **Трансляция стратегий.** Наши аргументы — флаги `winws` (`--dpi-desync=…`, `--hostlist=…`).
   У byedpi **другой** синтаксис. Нужна таблица перевода, как в `docs/research/zapret-configs.md` §1.5,
   только между winws и byedpi. Работа механическая, но объёмная.
4. **Списки и hosts.** На Android hosts правится только с root — значит основная ставка на
   `VpnService`-фильтрацию и DNS, а не на hosts.

#### Оценка трудозатрат (для одного разработчика)

| Этап | Оценка |
|---|---|
| Вынести переносимое ядро в .NET 9 библиотеку | 3–5 дней |
| MAUI-шелл: 6 экранов, настройки, логи, трей→уведомление | 1.5–2 недели |
| `VpnService` + tun + foreground + разрешения | 1–2 недели |
| Интеграция нативного движка (JNI + CMake, 4 ABI) | 1–2 недели |
| Трансляция стратегий winws → движок | 1 неделя |
| Тесты на реальных устройствах, Android 7…15, разные прошивки | 2–3 недели (и это не ускорить) |

**Итого: ~2–3 месяца** при аккуратной работе, и это **не** «портирование» — это второе приложение
с общим ядром данных.

#### Что реально стоит сделать вместо полного порта

1. **Вынести ядро в .NET 9 библиотеку уже сейчас** — это полезно и для десктопа (тестируемость),
   и станет фундаментом Android-версии. Дёшево, делается в любой момент.
2. **Общий формат данных**: `strategies.json`, списки, `fakes.json`, `scores.json` — одинаковые
   на обеих платформах. Тогда Android-версия читает те же файлы.
3. **Отдельное приложение на Kotlin** (как ByeByeDPI), а не MAUI: меньше слоёв, проще JNI,
   и можно переиспользовать чужой опыт по `VpnService`.

#### Юридическая мина

**ByeByeDPI — GPL-3.0.** Если брать их код или бандлить byedpi, Android-приложение обязано стать
GPL-3.0. Это **не** заразит десктопную версию, если это отдельные приложения с общим форматом
данных, а не общий код. Решение принять до первой строки.

#### Риски

- **Play Store**: приложения для обхода блокировок регулярно удаляют. Планировать распространение
  через GitHub Releases / F-Droid.
- **Разрешение VPN** — системный диалог, пользователь может отозвать в любой момент.
- **Батарея и фон**: Android убивает фоновые сервисы; нужен foreground-сервис с уведомлением.
- **Не блокирует десктоп.** Это отдельный продукт, не обязательство.

### P13 — Кроссплатформенность: Linux, CLI, GUI для всех `[ ]` ⭐ идея на будущее

> Записано со слов заказчика: «хочу поддержку Linux (автокомпил либ из bol-van), скрипт
> как у Zapret Manager, GUI и CLI версии для всех платформ, Android только GUI.
> .NET вроде кроссплатформенный, но надо обдумать универсально».

**Главная мысль, которую надо принять до первой строки:** .NET кроссплатформенный,
но **наша оболочка — нет**. WinForms + WebView2 + WinDivert — это три Windows-only
кирпича, и ни один из них не «перекомпилируется под Linux». Переезжает не приложение,
а **ядро**; оболочка пишется заново под каждую платформу.

#### 1. Что реально переносится (проверено по коду, не на глаз)

| Компонент | Linux | Android | Комментарий |
|---|---|---|---|
| `Core.Json`, `AtomicFile`, `Log`, `Settings` | ✅ | ✅ | пути через `Path.Combine`, разделители не хардкодить |
| `Core.Doh`, `Core.Resolver`, `Core.LocalDns` | ✅ | ⚠️ | сокеты и `HttpClient` везде; на Android свой DNS не нужен — там `VpnService` |
| `Lists.*` (списки, `HostsEditor`, `HostsFixes`) | ✅ | ⚠️ | hosts на Android не пишется (нужен root) |
| `Zapret.StrategyParser`, `StrategyStore` | ✅ | ✅ | это чистая модель данных, ценность одна и та же |
| `Orchestrator.ScoreStore`, `Bandit` | ✅ | ✅ | статистика переносится целиком |
| `Proxy.*` (MTProto WS) | ✅ | ⚠️ | `HttpClient`/сокеты есть, но на Android нужен `VpnService` или локальный прокси |
| `Diag.ConnectivityProbe`, `DeepProbe`, `Tcp16Test` | ✅ | ✅ | обычные сокеты |
| `Zapret.WinDivertInterop`, `Own.OwnEngine` | ❌ | ❌ | **это WinDivert**, драйвер Windows |
| `Zapret.WinwsSupervisor` | ❌ | ❌ | запускает `.exe` |
| `App.AppHost`, `MainForm`, `TrayController` | ❌ | ❌ | WinForms |
| `Core.SystemDns`, `BrowserDoh`, `AutoStartManager` | ❌ | ❌ | `netsh`, реестр, планировщик задач |
| `Diag.SystemChecks` | ⚠️ | ⚠️ | половина проверок Windows-специфична (`sc query`, `netsh`) |

Оценка: **переносится ~45% кода, и это самая ценная часть** (модель, списки, статистика,
пробы). Всё, что касается перехвата пакетов и оболочки, — своё на каждой платформе.

#### 2. Структура решения: три проекта вместо одного

```
src/AutoZapret.Core/      net9.0              — всё переносимое, БЕЗ Windows API
src/AutoZapret.Windows/   net9.0-windows      — WinForms + WebView2 + WinDivert + winws
src/AutoZapret.Linux/     net9.0              — Avalonia/GTK + nfqws
src/AutoZapret.Cli/       net9.0              — общий CLI поверх Core (+ платформенные адаптеры)
```

Правило, которое убережёт от расползания: **`Core` не ссылается ни на что платформенное**.
Как только в Core появляется `using System.Windows.Forms` или `[DllImport("WinDivert")]` —
переезд на Linux становится переписыванием с нуля. Это дешевле соблюсти сразу.

Платформенное прячется за интерфейсами:

```csharp
interface IPacketEngine { Task<string> StartAsync(Strategy s); Task StopAsync(); }
interface IDnsConfigurator { Task<string> EnableAsync(); Task<string> RestoreAsync(); }
interface IPrivilegeCheck { bool IsElevated { get; } Task<bool> RequestAsync(); }
```

Windows-реализация = `WinwsSupervisor` + `WinDivert`, Linux = `nfqws`, Android = `VpnService`.

#### 3. Linux: движок из bol-van

- `zapret` от bol-van — **исходники на C**, сборка `make`, зависит от `libnetfilter_queue`,
  `nfnetlink`, `libcap`, `zlib`. Никаких готовых `.exe`: на Linux это `nfqws` (userspace)
  + правила `nftables`/`iptables`, которые заворачивают трафик в NFQUEUE.
- **Автокомпиляция при первом запуске** (идея заказчика) — реально, но требует
  `build-essential`, `libnetfilter-queue-dev`, `libnfnetlink-dev`. Значит:
  * сначала проверяем, есть ли `nfqws` в PATH / в комплекте;
  * если нет — предлагаем `apt install` / `pacman -S` (не запускаем `sudo` молча);
  * собираем в `~/.local/share/autozapret/engine/` из исходников, скачанных с GitHub;
  * **если сборка не удалась — внятная ошибка с пакетами**, а не «не работает».
- Альтернатива, которую надо держать в голове: **не собирать, а поставлять готовый
  статический `nfqws`** под x86_64/aarch64. Сборка на машине пользователя — это
  компилятор, зависимости и 30 секунд ожидания; статический бинарь — 200 КБ и ноль проблем.
  Решение по лицензии: zapret — MIT, статическая сборка разрешена.
- Права: `CAP_NET_ADMIN` вместо UAC. Пакетом — `pkexec` или systemd-юнит, не `sudo` из GUI.
- Конфиги: те же `strategies.json`, но `--wf-tcp` → `--filter-tcp`, пути `/etc/...` → наши.

#### 4. CLI: один бинарь, режимы вместо отдельных программ

```
autozapret                      # GUI (если есть дисплей)
autozapret --cli status         # состояние
autozapret --cli start [--strategy id]
autozapret --cli probe          # что заблокировано
autozapret --cli test 5         # подбор
autozapret --cli lists update
autozapret --cli selftest
```

У нас уже есть почти весь CLI (`--selftest`, `--probe`, `--test-all`, `--diag-zip`,
`--stages`, `--sysdns`, `--flushdns`, `--own`). Не хватает: единой точки входа с
подкомандами, `--json` для машинного вывода (пригодится для скриптов и Zapret Manager-подобных
обёрток) и кодов возврата по смыслу, а не «0/1».

#### 5. GUI: чем заменить WinForms/WebView2

| Вариант | Плюсы | Минусы |
|---|---|---|
| **Avalonia** (.NET, MIT) | настоящий кросс-платформенный XAML, зрелый, нативный вид | вёрстку `web/` придётся переписать в XAML — **это главный минус**, у нас 40 КБ HTML |
| **Photino / WebView2-аналог** | HTML остаётся как есть | на Linux тянет `libwebkit2gtk`, на Android не работает |
| **Blazor Hybrid (MAUI)** | HTML+JS переиспользуется | MAUI на Linux не поддерживается официально (только community) |
| **Отдельный webview + локальный HTTP** | HTML один на все платформы, включая Android | нужен свой сервер, CSP, безопасность моста руками |

**Рекомендация:** держать UI как HTML (он уже написан и переносим на Android по P12) и
менять только «хост»: Windows — WebView2 (как сейчас), Linux — WebKitGTK через Photino
или свой минимальный хост, Android — `android.webkit.WebView`. Тогда `web/` — единственный
источник интерфейса, а не три копии.

**Цена:** мост `chrome.webview.postMessage` на Linux/Android другой. Значит, `send()`/`onMessage()`
в `app.js` уже сейчас надо держать в двух функциях (так и сделано, AGENTS.md п.4) и добавить
вторую реализацию транспорта, а не переписывать экраны.

#### 6. Порядок работ (если браться)

1. **Вынести `Core` без Windows-зависимостей** — 3–5 дней. Полезно уже сейчас: тестируемость,
   и это фундамент всех платформ. Риск нулевой, Windows-версия продолжает работать.
2. **CLI с подкомандами и `--json`** — 2–3 дня. Даёт скриптуемость и «как Zapret Manager».
3. **Linux-хост + nfqws** — 2–3 недели. Сначала ручная сборка движка, потом автокомпиляция.
4. **Android** — см. P12, это отдельные 2–3 месяца и отдельный продукт.

#### 7. Риски и решения

- **Ядро «поедет» и разъедется.** Держать один `Core` и три тонких хоста; общие данные
  (`strategies.json`, списки, `scores.json`) — один формат на всех.
- **Собственный движок (P10) на WinDivert не переносится.** На Linux аналог — NFQUEUE,
  на Android — tun. Это **три разные реализации**; общим остаётся только разбор пакетов
  (`TcpPacket`) и логика техник, её и надо держать платформенно-нейтральной.
- **Разные права.** Windows — UAC/админ, Linux — `CAP_NET_ADMIN`/pkexec, Android — диалог
  `VpnService`. Один интерфейс `IPrivilegeCheck`, три реализации.
- **Сборка на машине пользователя — источник боли.** Предпочитать готовые статические
  бинари; автокомпиляцию оставить как fallback с внятными сообщениями о пакетах.
- **Не распыляться.** Windows-версия — основной продукт. Linux/Android — отдельные ветки
  работы, которые не должны тормозить P10/P11.

### P14 — Режим службы Windows `[~]` ⭐ ближайшая идея

> Записано со слов заказчика: «сделать возможность запускать службой, т.е. 4 кнопки
> нужно будет Установить, Удалить, Запустить, Остановить и следовательно
> переключаться между режимом службы и обычным режимом».

**Сделано (2026-11-05):** тело службы (`ServiceHost`: P/Invoke
`StartServiceCtrlDispatcher` / `RegisterServiceCtrlHandlerEx` / `SetServiceStatus`),
`ServiceRunner` (движок + присмотр с перезапуском до 5 раз),
`ServiceManager` (install / uninstall / start / stop / query через `sc.exe`),
`--service [install|uninstall|start|stop|status]` в `Program.cs`, карточка
«Служба Windows» в настройках с четырьмя кнопками, взаимное исключение с кнопкой
питания (заблокирована с подписью «СЛУЖБА», когда обход держит служба),
CI-проверка «тело службы не зависает».

Две ловушки, поймавшие себя сами:
* `sc create binPath= "...exe" --service` → SCM запускает **без** действия, и
  при действии по умолчанию `status` служба мгновенно выходила (ошибка 1053).
  Теперь «нет действия» = «работай как служба», а `--service status` — явно;
* служба стартует от `LocalSystem`, у которого свой `%LocalAppData%` — она
  читала бы **чужой** `settings.json` и запускала стратегию по умолчанию.
  Теперь `Paths.ForcePortable()` в режиме службы: данные рядом с exe.

**Осталось:** проверка на живой машине с админом (установка → перезагрузка →
работает до входа в систему), и обновление приложения при работающей службе
(`sc stop` → обновить → `sc start`).

**Зачем это нужно на самом деле.** Сейчас обход живёт, пока открыто окно. Закрыл
программу — обход умер. Автозапуск через планировщик (`AutoStartManager`, P9) это
частично лечит, но он запускает **приложение с окном**: при входе в систему
появляется окно (или иконка в трее), и всё это живёт в сессии пользователя.
Служба решает три вещи, которые планировщик не решает:

1. **Обход работает до входа в систему** — сеть поднимается раньше, чем кто-то
   нажал «войти».
2. **Не нужен вход в систему вообще** — сервер, машина без монитора, RDP-хост.
3. **Переживает выход из сеанса** — пользователь вышел, обход остался.

#### 1. Почему это не «просто sc create»

`sc create` с нашим GUI-процессом **не работает**: SCM требует, чтобы процесс в
течение 30 секунд вызвал `StartServiceCtrlDispatcher`, иначе убивает его с ошибкой
1053 «не ответил вовремя». Значит нужен отдельный режим запуска:

```
AutoZapret.exe --service          # тело службы: dispatcher + работа движка
```

и `Program.cs` должен развести это **до** создания любого окна: служба не имеет
права ни на WinForms, ни на WebView2 (session 0 isolation — окно там не появится
никогда, а попытка создать его вешает процесс).

#### 2. Что придётся написать самим (NuGet нельзя)

`Microsoft.Extensions.Hosting.WindowsServices` — это NuGet, а он запрещён
(AGENTS.md п.2). Значит P/Invoke, ~150 строк:

| Функция | Зачем |
|---|---|
| `StartServiceCtrlDispatcher` | связать процесс с SCM, получить control handler |
| `RegisterServiceCtrlHandlerEx` | ловить STOP / SHUTDOWN / PRESHUTDOWN |
| `SetServiceStatus` | рапортовать STARTING → RUNNING → STOPPED (иначе SCM решит, что процесс мёртв) |
| `CreateService` / `DeleteService` / `StartService` / `ControlService` | четыре кнопки |
| `OpenSCManager` / `OpenService` / `QueryServiceStatus` | состояние для интерфейса |

Альтернатива без P/Invoke — гонять `sc.exe` через `cmd /c chcp 437 &` (как уже
делаем для `netsh` и `sc query` в `SystemChecks`). Для **установки** и **удаления**
этого достаточно и проще. Но **тело службы** всё равно требует P/Invoke:
`StartServiceCtrlDispatcher` из командной строки не вызвать.

Компромисс, который стоит попробовать первым: тело службы — P/Invoke (150 строк,
один раз), управление — через `sc.exe` (уже работает, кодировки уже разрулены).

#### 3. Что должна делать служба

Только движок. Никакого UI, трея, прокси и диагностики:

```
--service  →  читает settings.json
           →  выбирает движок (winws / winws2 / свой)
           →  запускает выбранную стратегию или технику
           →  пишет лог в data\logs
           →  на STOP гасит дерево процессов и ждёт выгрузки WinDivert
```

Прокси Telegram (P6) в службу **не тащить**: он слушает порт и работает от имени
пользователя, смешивать два разных сервиса в одном процессе — это два независимых
жизненных цикла в одном месте.

#### 4. Четыре кнопки и переключатель режима

Карточка «Служба» на экране «Настройки»:

| Кнопка | Что делает | Права |
|---|---|---|
| **Установить** | `sc create AutoZapret binPath= "<exe>" --service` + описание + восстановление при падении | админ |
| **Удалить** | `sc stop` → ждать STOPPED → `sc delete` | админ |
| **Запустить** | `sc start` | админ |
| **Остановить** | `sc stop` → polling до STOPPED (как в `WinwsSupervisor.Stop`) | админ |

Плюс состояние: `не установлена / остановлена / работает / остановка…`.

**Переключатель «режим службы ↔ обычный режим»** — это не отдельная функция, а
следствие. Правила:

- пока служба **работает**, кнопка питания в интерфейсе **заблокирована** с
  объяснением «обход запущен службой» — иначе два перехватчика подерутся за
  WinDivert, и это будет выглядеть как «обход не работает»;
- при включении режима службы обход из приложения гасится, приложение
  превращается в пульт управления;
- `settings.zapret.serviceMode` уже существует в `Settings.cs` и сейчас **мёртвый**
  (объявлен, сохраняется, нигде не читается) — P14 его оживит.

#### 5. Грабли, которые надо помнить заранее

| Грабля | Решение |
|---|---|
| Ошибка 1053 «не ответил вовремя» | `StartServiceCtrlDispatcher` вызывать первым делом в `--service`, до любой инициализации |
| Служба стартует от `SYSTEM`, а данные в `%LocalAppData%` пользователя | служба обязана работать в **portable**-режиме: данные рядом с exe, а не в профиле |
| WinDivert из session 0 | работает (это драйвер, не UI), но проверить на чистой машине |
| `sc stop` вернулся, драйвер ещё жив | polling до `STOPPED` + пауза 1500 мс (уже знаем) |
| Служба и GUI одновременно запускают движок | взаимное исключение по состоянию службы, кнопка питания гаснет |
| Антивирус и служба | `WinDivert64.sys` уже флагается; установка службы добавит подозрительности — нужен честный раздел в README |
| Обновление приложения при работающей службе | `sc stop` → обновить → `sc start`, иначе файлы заняты |
| Пользователь забыл про службу и удалил папку | служба останется в SCM и будет падать при старте — при запуске приложения проверять и предлагать «Удалить» |

#### 6. Оценка

| Работа | Время |
|---|---|
| P/Invoke для тела службы (`StartServiceCtrlDispatcher`, `SetServiceStatus`) | 1–2 дня |
| `--service` режим в `Program.cs` + запуск движка без UI | 1 день |
| Управление через `sc.exe`: установка, удаление, старт, стоп, состояние | 1 день |
| Взаимное исключение с GUI + переключатель режима | 1 день |
| Тесты: чистая машина, служба от SYSTEM, перезагрузка, удаление папки | 1–2 дня |

**Итого ~1 неделя**, и это без прокси и без UI внутри службы.

#### 7. Что НЕ надо делать

- **Не пихать UI в службу.** Session 0 isolation: окно не появится, WebView2 не
  запустится, процесс зависнет. Служба — только движок.
- **Не делать службу единственным способом.** Обычный режим остаётся основным:
  большинству людей хватает «открыл программу — включил обход».
- **Не ставить службу молча.** Только по явной кнопке и с предупреждением, что
  обход будет работать всегда, даже когда программа закрыта.

### P15 — SmartDNS: разделение DNS по правилам `[ ]` ⭐ идея от друзей

> Записано со слов заказчика: «была такая штука СмартДНС… у тебя есть основной DNS,
> а есть ещё второстепенный, и в итоге вывод одного запроса через один DNS, а вывод
> другого — через тот, который ты задал сам».

**Что это по механике.** Не «второй DNS на всякий случай», а **маршрутизация запросов
по правилам**: для каждого имени решается, каким резолвером его спрашивать. У нас уже
есть все детали, из которых это собирается, — не хватает только правила выбора.

Классический SmartDNS (dnsmasq-china-list, AdGuard Home, mosdns) делает ровно три вещи:

1. **Разделение по домену.** `*.youtube.com` → через DoH (обход DNS-заглушки),
   `*.bank.ru` → через системный DNS провайдера (быстрее и «легально»).
2. **Сравнение ответов.** Спросить оба резолвера и выбрать тот ответ, который
   **реально коннектится** (у нас для этого уже есть `DeepProbe`/`ConnectivityProbe`).
   Так лечится подмена: провайдер отдаёт `198.18.0.x`, а DoH — настоящий адрес.
3. **Свой статический ответ.** `example.com → 1.2.3.4` без похода в сеть вообще.

**Почему это нам особенно нужно.** У заказчика провайдер подменяет DNS
(`198.18.0.x`), и Flowseal «работает, потому что у браузера свой Secure DNS». То есть
сейчас обход зависит от того, догадался ли человек включить DoH **в браузере**. Свой
SmartDNS снимает эту зависимость: правило живёт в программе, а не в настройках Chrome.

#### Что уже есть (не надо писать заново)

| Компонент | Что даёт | Чего не хватает |
|---|---|---|
| `Core.LocalDns` | UDP-листенер на 127.0.0.1:53, кэш, `Rewrite` (подмена ID), `ServFail` | один upstream на всё, нет правил |
| `Core.Doh` | DoH-клиент поверх `HttpClient`, `DohServers` (Cloudflare/Google/Quad9) | — |
| `Core.Resolver` | системный резолв + `SystemLooksHijacked` | нет «спросить два и сравнить» |
| `Core.SystemDns` | перевод системы на 127.0.0.1 (Win10+) | — |
| `Core.DnsGuard` | детект fake-IP (`198.18.0.0/15`) | не используется для выбора ответа |
| `Diag.ConnectivityProbe` | реальный коннект к адресу | не вызывается из DNS-пути |

#### Что писать

1. **`DnsRule`** — домен/суффикс + действие:
   `doh:<сервер>` | `system` | `static:<ip>` | `block` | `fastest`.
   Порядок = приоритет, первый подходящий выигрывает (та же логика, что в `OwnProfileSet`).
2. **`DnsRouter`** — выбор upstream по правилу. Один вход: `Route(question) → upstream`.
   Отдельный класс, а не `if` внутри `LocalDns`: правила — это данные, и они должны
   тестироваться без сокета.
3. **`DnsRace`** (режим `fastest`) — спросить два резолвера параллельно, взять первый
   валидный ответ; при подозрении на подмену (fake-IP или приватный адрес на публичном
   имени) — не доверять ему и спросить второй.
4. **Правила по умолчанию** — данные, не код: `assets/dns/rules.json`.
   Стартовый набор: всё из `list-general.txt` → DoH, банки/госуслуги → system,
   `*.local`/`*.lan` → system, остальное → DoH с fallback на system.
5. **UI** — карточка «DNS по правилам» в диагностике: список правил, режим
   (`только DoH` / `правила` / `сравнение`), счётчики попаданий по правилам.
6. **CLI** — `--dns-route example.com` → показать, каким резолвером пойдёт и что вернул.

#### Грабли (заранее)

| Грабля | Почему |
|---|---|
| **Порт 53 занят `svchost`** | На машине заказчика уже так: `SystemDns` включить нельзя. Значит основной режим — **не** перехват 53, а `--dns-route` и настройка браузера. Свой листенер — опция, не основа |
| **DoH-сервер по имени резолвить нечем** | `https://1.1.1.1/dns-query` — уже так и сделано (`DohServers` по IP). Иначе курица и яйцо |
| **Кэш на ответы разных upstream** | Ключ кэша обязан включать upstream, иначе ответ «через банк» уедет на youtube и наоборот. Текущий `LocalDns.CacheKey` этого не знает — расширить |
| **DNS over TCP** | Ответ >512 байт приходит с флагом TC, клиент повторит по TCP. Сейчас `LocalDns` этого не умеет — либо поддержать, либо честно отдавать TC |
| **`fastest` = задержка на каждый запрос** | Два запроса вместо одного. Только для доменов из списка, никогда — глобально |
| **Приватный адрес в ответе на публичное имя** | Это и есть признак подмены (роутер/провайдер). `DnsGuard` уже это умеет — использовать при выборе ответа |
| **Правила и hosts пересекаются** | Порядок обязан быть один и явный: hosts → правила → upstream. Иначе «я же прописал в hosts» перестаёт работать без причины |

#### Оценка

`DnsRule` + `DnsRouter` + тесты — **день**. `DnsRace` + сравнение ответов — ещё день.
Правила по умолчанию и UI — полдня. Итого **~2.5 дня**, и это без перехвата 53.

### P16 — SOCKS5 с логином и паролем `[ ]` ⭐ идея от друзей

> Записано со слов заказчика: «сделать бы режим прокси раздачи, типа SOCKS5 с логпассом
> для безопасности. Это будет полезно и для будущих VPN фич и даже сейчас».

**Зачем.** Сейчас у нас один локальный прокси — MTProto WS для Telegram, и он слушает
`127.0.0.1`. SOCKS5 даёт другое: **раздачу интернета на другие устройства** (телефон,
телевизор, второй ноут), причём с авторизацией, чтобы этим не пользовался весь подъезд.

Это же — фундамент для P11: Xray/Mihomo умеют отдавать наружу SOCKS, и наша обвязка
(порт, пароль, тумблер, статистика) переиспользуется как есть. И для P12: на Android
локальный SOCKS — штатный способ завернуть трафик в `VpnService`.

#### Почему SOCKS5, а не HTTP-прокси

| | SOCKS5 | HTTP CONNECT |
|---|---|---|
| UDP (QUIC, игры) | ✅ `UDP ASSOCIATE` | ❌ |
| Любой протокол, не только HTTP | ✅ | ⚠️ только через CONNECT |
| Авторизация | ✅ логин/пароль (RFC 1929) | ✅ Basic, но в открытом виде |
| Клиенты | есть везде | есть везде |

UDP важен: без него QUIC не поедет, а половина YouTube — QUIC.

#### Что писать (и чего НЕ писать)

**Писать:**

1. **`Socks5Server`** — RFC 1928: greeting (методы `0x00` no-auth, `0x02` user/pass),
   `0x01` CONNECT (IPv4/IPv6/домен), `0x03` UDP ASSOCIATE, reply-коды.
   Поток на соединение, как в `TgProxyServer` — там уже отработан этот каркас.
2. **`Socks5Auth`** — RFC 1929, сравнение пароля **за постоянное время**
   (`CryptographicOperations.FixedTimeEquals` в .NET 9; вручную — XOR-накопление).
   Логин и пароль генерируются `RandomNumberGenerator`, как секрет прокси.
3. **Привязка.** По умолчанию `127.0.0.1`. `0.0.0.0` — только явным выбором,
   и **не запретом, а окном с отсчётом** (см. ниже). Запрет не работает: человек
   обходит его правкой конфига, а предупреждение, которое нельзя пролистать
   за секунду, работает. Открытый SOCKS в домашней сети — это открытый прокси
   для всех, кто в неё попал, и цена ошибки — чужой трафик с вашего адреса.
4. **Статистика** — соединений, байт туда/обратно, отказов авторизации.
   Отказы важны: их рост = кто-то подбирает пароль.
5. **UI** — карточка «Прокси для устройств»: тумблер, адрес, порт, логин, пароль
   (скрыт, по кнопке), «показать ссылку», список подключённых клиентов по IP.

#### Окно «Вы точно уверены?» — и почему отсчёт, а не запрет
Записано со слов заказчика: «сделай пусть можно, но с жёстким окошком, как в Xiaomi:
"ВЫ ТОЧНО УВЕРЕНЫ? Пользуйтесь ТОЛЬКО в локальной сети!" Отмена сразу доступна, а для
ОК надо ждать 30 секунд, чтобы подумать. А потом типа "Ну ладно, я предупредил,
всё на ваш страх и риск, ещё раз: пользуйтесь ТОЛЬКО в локальной сети"».

Механика окна (уже реализована как `dangerConfirm()` в `web/app.js` + разметка
`#danger-overlay`, переиспользуется для других необратимых действий):

1. Затемнение и размытие фона — читать список за окном и решать «а, там нормально» нельзя.
2. **«Отмена» активна сразу** и всегда. Фокус по умолчанию на ней: Enter без чтения
   отменяет, а не подтверждает. Это осознанно несимметрично.
3. **«ОК» заблокирована и тикает**: «Подождите 30…» → «…29» → … Отсчёт через
   `setInterval`, а не блокировка потока: окно не должно выглядеть зависшим.
4. После отсчёта кнопка становится «Да, я понимаю риск».
5. **Второе предупреждение** — короткое, злое, красной полосой:
   «Ну ладно, я предупредил. Всё на ваш страх и риск. Ещё раз: только локальная сеть».
   Только после него — запуск.
6. `Esc` = отмена (привычка сильнее кнопки, и это безопасное действие).

Для SOCKS5 при выборе `0.0.0.0` без пароля: `wait: 30`, текст — «ВЫ ТОЧНО УВЕРЕНЫ?
Пользуйтесь ТОЛЬКО в локальной сети! Любой, кто попадёт в вашу сеть, сможет ходить
в интернет через ваш компьютер и ваш адрес».

Почему 30 секунд, а не 5: это ровно то время, за которое человек либо дочитывает
и отменяет, либо понимает, что ему действительно надо. Пять секунд пролистываются
не глядя.

Почему не запрет: запрет выглядит как поломка («почему нельзя?»), и его обходят
правкой `settings.json`. Отсчёт объясняет, что происходит, и оставляет выбор
за человеком — но выбор осознанный.

**Шкала ожидания** (записано со слов заказчика: «с hosts секунд 1–3–5, это не такое
опасное действие, а вот с прокси 25–30, чтобы пользователь одумался»). Ожидание
пропорционально цене ошибки, а не единое на всё: если ждать 30 секунд там, где
восстановление в один клик, человек начнёт жать «ОК» не читая — и привычка перенесётся
на окно, где это критично.

| Действие | `wait` | Почему столько |
|---|---|---|
| Пересоздать hosts | **5 с** | резервная копия есть, «Восстановить» рядом. Неприятно, но не смертельно |
| Удалить службу | **10 с** | обход перестанет работать до входа в систему, но вернуть можно установкой |
| Слушать SOCKS5 на `0.0.0.0` | **30 с** | последствие видно не сразу и не здесь: чужим трафиком с вашего адреса может заинтересоваться кто-то другой. Это и есть то «одумался» |

Ожидание — единственная защита, которая не обходится: остальные варианты (запрет,
галочка «я понимаю», второй диалог подряд) пролистываются на автомате за секунду.



**НЕ писать:**

- ❌ **BIND** — не нужен никому и добавляет поверхность атаки.
- ❌ Свой резолв домена на стороне прокси с «умным» выбором — пусть резолвит клиент
  или системный DNS. Иначе получится второй DNS-стек (см. P15) в самом неудобном месте.
- ❌ Прозрачный прокси через WinDivert — это уже P11/TUN, другая задача.

#### Грабли

| Грабля | Почему |
|---|---|
| **Открытый SOCKS = открытый прокси** | `0.0.0.0` без пароля превращает машину в узел для чужого трафика. Не запрет, а окно с отсчётом 30 с и вторым предупреждением (`dangerConfirm`) — запрет обходят правкой конфига, а прочитанное предупреждение работает |
| **Логин/пароль в лог** | Никогда. В лог только «клиент 192.168.1.5 авторизован», без секрета |
| **Сравнение пароля посимвольно** | `==` выходит на первом различии — по времени подбирается. Постоянное время обязательно |
| **UDP ASSOCIATE и NAT** | Клиент ждёт ответы на свой UDP-порт; сервер обязан помнить привязку и не путать клиентов. Проще: отдельный сокет на ассоциацию, TTL 60 с |
| **Порт занят** | 1080 обычно занят чем-то. Ошибку bind показывать человеческим текстом (как `10048 → «порт занят»` в `TgProxyServer`) |
| **Брандмауэр** | При первом слушании на `0.0.0.0` Windows спросит разрешение. Без ответа — тишина и «не работает». Проверять и подсказывать |
| **IPv6** | Клиент может прийти по IPv6, а CONNECT попросить на IPv4-литерал. Обе ветки, как в `TcpPacket`/`UdpPacket` |
| **Прокси и обход одновременно** | Если `winws` перехватывает, локальные соединения прокси тоже проходят через desync. Не ломается, но в логах путаница: помечать свои соединения |

#### Оценка

`Socks5Server` + авторизация + тесты (greeting, auth, CONNECT, отказ, UDP) — **два дня**.
UI и статистика — полдня. Итого **~2.5 дня**, и это переиспользуется в P11 целиком.

### P17 — Свои конфиги: импорт `.bat`, обмен, «мои стратегии» `[ ]` ⭐ идея от друзей

> Записано со слов заказчика: «сделать импорт кастомных конфигов из батников…
> и сделать легкий импорт/экспорт, чтобы можно было поделиться с другом своим конфигом».

**Где мы сейчас.** `.bat` уже разбирается — `StrategyParser.ParseBat` читает команду
`winws`, подставляет `${BIN}`/`${LISTS}`, и весь список стратегий когда-то так и был
импортирован. Но наружу этого нет: пользователь может только выбрать из 44 готовых.
Своей стратегии добавить некуда — `strategies.v1.json` считается данными поставки.

**Что нужно.**

1. **`CustomStrategies`** — отдельный набор рядом с поставкой: `assets/strategies/custom.json`
   (или `data/strategies/custom.json`, решим по тому, должна ли она ездить с пакетом).
   Идентификаторы с префиксом `custom.`, чтобы не столкнуться с `flowseal.*`/`zapret2.*`.
2. **Импорт `.bat`** — файловый диалог, разбор, предпросмотр **до** сохранения:
   что за движок, какие профили, какие файлы он ждёт и есть ли они. Кнопка
   «Добавить» появляется только если `Preflight` не нашёл блокеров.
3. **Экспорт одного конфига** — один файл `*.azconf.json` с версией схемы,
   содержимым стратегии и **без путей пользователя**: только `${BIN}`/`${LISTS}`.
   Плюс короткая подпись «от кого», чтобы друг видел, чей это конфиг.
4. **Импорт чужого конфига** — с проверкой: схема совпадает, обязательные поля
   на месте, ссылки только на наши плейсхолдеры. **Никаких URL и абсолютных путей
   в конфиге** — иначе «поделиться с другом» превращается в «загрузи и выполни».
5. **Список стратегий** показывает бейдж «своя» и позволяет удалить/скопировать.

**Грабли, которые надо помнить заранее.**

| Грабля | Почему |
|---|---|
| `.bat` бывает не одним `winws`, а десятью строками с `set`, `goto`, `if` | Парсер уже пропускает служебное, но **надо показать**, что именно не разобрано, а не молча взять первую команду |
| Кодировка `.bat` | cp866/UTF-8/UTF-16 — `DetectEncoding` есть, но пользовательский файл может быть в OEM-кодировке без BOM: нужен предпросмотр текста |
| Импорт с тем же id | Перезапись чужой стратегии молча — худший вариант. Либо новый id, либо явный вопрос |
| Экспорт с абсолютными путями | Конфиг с `C:\Users\Вася\...` у друга не работает и выдаёт, где вы живёте |
| Импорт с `--hostlist=C:\Windows\...` | Это уже не конфиг, а чтение произвольных файлов движком. Разрешать только `${LISTS}`/`${BIN}` |
| Свои конфиги и обновление поставки | Обновление не должно их затирать: наша стратегия — отдельный файл, а не запись в `strategies.v1.json` |

**Оценка:** импорт + предпросмотр + экспорт — **2–3 дня**. Модель данных уже есть,
работы в основном вокруг UI и проверок.

### P18 — Умный генератор и автоподбор своей стратегии `[ ]` ⭐ идея от друзей

> Записано со слов заказчика: «сделать свой генератор конфигов, умный, подбор
> собственной стратегии, чтобы это тоже в кастом себе записывать».

**Что это.** Не «ещё один автопилот», а **сборка конфига под конкретную сеть**:
программа сама пробует техники и параметры, находит рабочую комбинацию и
**сохраняет её как свою стратегию** (P17), а не просто переключается на чужую.

База уже есть:
* `TechniqueTester` — прогон всех техник на реальном DPI с оценкой;
* `ScoreStore` + `Bandit` + `WilsonLowerBound` — статистика по сетям;
* `WinwsCompat` — перевод найденного в аргументы `winws` и обратно;
* `OwnProfile`/`OwnProfileSet` — модель «техника + порты + цели».

**Что писать.**

1. **Генератор конфига** из найденной техники: `TechniqueOptions` → `Strategy`
   (аргументы `winws`) и/или в `OwnProfileSet`. Один источник правды: генератор
   пишет **ту же модель**, что читает парсер, иначе получится два формата.
2. **Поиск** — не «перебрать 22 × N»: сначала грубая сетка (техника × ключевые
   параметры), потом локальное уточнение вокруг лучших. С ограничением времени
   и с честным «нашёл 6/6, счёт 91» в отчёте.
3. **Сохранение** найденного: «Сохранить как мою стратегию» → `custom.*` с именем
   по сети/дате, чтобы через месяц было понятно, откуда оно.
4. **Осторожность с автоматикой:** генератор не должен молча подменять рабочую
   стратегию. Только предложение + кнопка.

**Грабли.**

| Грабля | Почему |
|---|---|
| Генератор, который пишет «идеальную» стратегию по 4 пробам | 4 пробы ничего не доказывают. Wilson lower bound уже есть — использовать, а не среднее |
| Перебор без лимита времени | 64 стратегии × 4 пробы — это 12+ минут. Пользователь закроет окно и не вернётся |
| Найденное зависит от сети | Сохранять **вместе с отпечатком сети** (`NetworkFingerprint`), иначе через месяц «моя стратегия» не работает и непонятно почему |
| Сгенерированный конфиг не проходит Preflight | Генерировать и сразу проверять: файлы фейков, списки, lua для v2 |

**Оценка:** генератор + сохранение — **2 дня**; поиск с уточнением — ещё **2–3**.

### P19 — Визуальный конструктор конфигов (нодовый редактор) `[ ]` ⭐ идея от друзей

> Записано со слов заказчика: «свой ручной конструктор конфигов, удобный редактор,
> как в нодах, только с прилипкой и драг-дропами, как в Scratch или нодовом редакторе
> MCreator».

**Идея.** Конфиг — это граф: «источник (порт/домены) → техника → параметры →
fooling». Такой граф читается глазами, в отличие от 108 аргументов в строку.

**Ключевое архитектурное решение: редактор — это ВИД, а не второй формат.**
Он редактирует ту же `Strategy`/`OwnProfileSet`, что читает движок. Иначе появятся
два представления одного смысла, и они разойдутся — это уже было с v1/v2.

**Что нужно.**

1. **Холст с нодами** — HTML+CSS+JS, без библиотек (NuGet/JS-пакеты запрещены).
   Перетаскивание, прилипание к сетке, соединение портов, зум.
2. **Типы нод** по модели, а не по фантазии:
   `источник` (TCP/UDP порты, hostlist, ipset, исключения) → `техника`
   (split/multisplit/fake/…) → `параметры` (позиции, повторы, seqovl) →
   `fooling` (badsum/badseq/md5sig/datanoack) → `фейк` (`.bin` из библиотеки).
3. **Живая проверка**: несовместимые порты не соединяются, обязательные поля
   подсвечены, а `Preflight` гоняется по графу до сохранения.
4. **Обратный импорт**: граф должен строиться из существующей стратегии, иначе
   редактор умеет только создавать с нуля, а это половина пользы.
5. **Экспорт в оба вида**: `winws`-аргументы (для zapret) и профили (для своего
   движка) — через тот же `WinwsCompat`.

**Почему это дорого и почему всё равно стоит.** Холст с прилипанием и соединениями —
это ~1500 строк JS и много мелочей (тачпад, масштаб, отмена). Но это единственная
часть программы, где человек **видит**, что происходит с его трафиком, а не читает
список стратегий. И это же лучший способ разобраться, почему чужая стратегия
не работает.

**Грабли.**

| Грабля | Почему |
|---|---|
| Второй формат конфига | Ноды должны сериализоваться в существующую модель, иначе экспорт в winws разъедется с реальностью |
| Свобода «соедини всё со всем» | Невалидные комбинации (UDP-техника на TCP-профиле) должны быть невозможны на уровне типов портов, а не проверки после |
| Undo/redo «потом» | Без отмены нодовый редактор бесит с первой минуты |
| Координаты в файле конфига | Позиции нод — это UI-состояние; хранить отдельно, иначе конфиг, которым поделились, откроется кашей |
| `!domain` и исключения | Рисовать явно, как отдельную ноду «исключить», иначе их снова примут за цель |

**Оценка:** холст + ноды + сериализация — **5–7 дней**. Обратный импорт и проверки —
ещё 2. Итого **~1.5 недели**, и это уже полноценная фича, а не «настройки».

### P20 — Замечания с живой машины (2026-11-05) `[~]`

> Шесть пунктов, пришедших одним сообщением после первого живого запуска.
> Порядок — «от лёгкого к тяжёлому», как и просили.

#### P20.1 Светлая и OLED-темы `[x]`

Три темы: `dark` (по умолчанию), `light`, `oled` (чистый чёрный). Переключение —
атрибут `data-theme` на `<html>`, выбор — в настройках, рядом с языком.

Главная работа была не в «поменять фон», а в том, чтобы **вынести всё
захардкоженное в переменные**: фон логов (был `#07090F`), цвета строк лога,
фон кнопки питания, подписи на плашках. Иначе светлая тема получалась бы
«белое окно, а внутри чёрный терминал».

| Грабля | Что сделано |
|---|---|
| `select.value` при отсутствии пункта молча ставит первый | выбор темы проходит через `hasOption()` |
| мигание тёмным при старте | выбор дублируется в `localStorage` и применяется до первого ответа ядра |
| `Normalize()` знает не все значения | `dark`/`light`/`oled` в списке, отдельная проверка на каждое значение в selftest |

#### P20.2 Размытие при масштабе 125 % `[x]`

Причина: `Application.SetHighDpiMode` **не вызывался вообще**. Свойство проекта
`<ApplicationHighDpiMode>PerMonitorV2</ApplicationHighDpiMode>` только генерирует
`ApplicationConfiguration.Initialize()`, а мы настраиваем WinForms руками — режим
оставался SystemAware, и Windows растягивала окно из 100 %. Лечится одним вызовом
(`DpiSetup.Apply()`), selftest проверяет, что режим действительно включился.

#### P20.3 Подбор стратегий не отменялся `[x]`

Кнопка работала, `diag.cancel` доходил, но токен проверялся **только перед
следующей стратегией**. Внутри одной итерации было `Thread.Sleep(5 c)` и пробы
с таймаутами по 8 с — итого до ~30 с между нажатием и реакцией, что неотличимо
от «кнопка не работает».

Теперь: ожидание после старта и пауза на выгрузку драйвера — через
`WaitHandle.WaitOne`, отмена проверяется сразу после `Start` и передаётся в
`CheckAll`. Selftest: с уже отменённым токеном перебор не запускает ни одной
стратегии и возвращается за единицы миллисекунд.

#### P20.4 Свой движок резал исходящую скорость `[x]`

Наблюдение: «zapret 1 режет, zapret 2 нет, наш режет сильнее zapret 1 — и только
исходящую». Это не совпадение: фильтр WinDivert был
`tcp.PayloadLength > 40`, то есть в user mode забирался **каждый исходящий пакет
с данными** (загрузка файла, отдача экрана, отправка сообщения). Входящие
подтверждения мелкие и под условие не попадали — отсюда «только исходящая».

Техника всё равно применяется к ClientHello, поэтому фильтр сужен до него:
`tcp.PayloadLength >= 6 and tcp.Payload[0] == 0x16 and tcp.Payload[1] == 0x03
and tcp.Payload[5] == 0x01`. Исключение — профили с `--dpi-desync-any-protocol`:
им нужен любой payload, и для них фильтр остаётся широким (`NeedsAnyPayload`).

#### P20.5 Показ экрана в Discord на своём движке `[x]`

Голос работал, показ экрана — нет. Причина: UDP-ветка узнавала только QUIC
(0xC0) и STUN (cookie `0x2112A442`). Голос начинается со STUN, а медиапоток
показа экрана — с **DTLS** (`0x16 0xFE…`), который не считался «нашим»: профиль
есть, техника выбрана, фейк не ушёл.

Добавлено распознавание DTLS и тип пакета в ключе «первого пакета потока»:
голос (STUN) и экран (DTLS) на одном пятикортеже теперь не мешают друг другу.

> Требует живой проверки: без второго человека и работающего DPI это не
> проверить, поэтому в ROADMAP стоит `[x]` по коду, но не по факту.

#### P20.6 Telegram: внешний релей `[~]`

Прямой `kws*.web.telegram.org` в этой сети не проходит вообще (блокировка по
адресу). Прокси готов и корректен, но нужен транспорт.

**Сделано (транспорт и UX):**

* `WsTunnel` — TCP-туннель через WebSocket: `wss://релей/?host=...&port=443`,
  поверх него TLS к Telegram и обычный `/apiws`. Релей не видит ни TLS, ни
  MTProto — только байты.
* `WsStream` — `Stream` поверх бинарных кадров (иначе `SslStream` не с чем
  работать). Чтение бесконечное по таймауту: сессия Telegram может молчать
  минутами, и обрывать её по «нет данных» нельзя.
* Настройка `ProxyRelay` — **список** через запятую/пробел/перевод строки.
  Пробуются по порядку, как маршруты: один воркер удалили — идём к следующему.
  Пауза «всё лежит» к релею не применяется: это другой транспорт.
* Кнопка **«Проверить»** — `relay.test` → туннель + TLS + `/apiws`, результат
  одной строкой. Причина отказа из close-кадра воркера показывается человеку.
* Кнопка **«Как сделать свой?»** — инструкция внутри программы, код воркера
  вшит в exe (`web/relay/worker.js` → `Resources.RelayWorker`) и копируется
  одной кнопкой. Копия в разметке разошлась бы с настоящей.
* `AutoZapret.exe --relay-check <адрес>` — та же проверка из консоли.
* `docs/relay-cloudflare-worker.md` — та же инструкция текстом.
* `?probe=host:port` в воркере — диагностика без WebSocket: сразу видно, что
  именно запретил Cloudflare, вместо «Stream was cancelled».

**Проверено:** цепочка «WS → TLS → /apiws» прогоняется на локальном макете
релея (Node, самоподписанный TLS) — `--relay-check ws://127.0.0.1:8770/`
проходит за 90 мс.

**Ждёт:** на `cdn.dartpower.workers.dev` пока старый код — `?probe=` отвечает
426 (старая версия проверяет Upgrade раньше probe). После деплоя нового кода
из `web/relay/worker.js` — проверить и включить.

## 10. Порядок работ (сводно)

```
P0 Фундамент ──► P1 Движок v1 ──► P2 UI v1 ──► P3 Фейки/списки ──► P4 Диагностика/автоподбор
                                                     │
                                                     ├──► P5 Обновления
                                                     ├──► P6 TG Proxy
                                                     ├──► P7 zapret2
                                                     ├──► P8 Оркестратор
                                                     ├──► P9 Полировка
                                                     ├──► P10 ⭐ свой движок
                                                     ├──► P11 ⭐ Mihomo / Xray (комбайн)
                                                     ├──► P12 ⭐ Android-версия (самое последнее)
                                                     ├──► P13 ⭐ Linux + CLI + GUI для всех
                                                     ├──► P14 ⭐ режим службы Windows
                                                     ├──► P15 ⭐ SmartDNS (правила)
                                                     ├──► P16 ⭐ SOCKS5 с паролем
                                                     ├──► P17 ⭐ свои конфиги (импорт/экспорт)
                                                     ├──► P18 ⭐ генератор и подбор
                                                     └──► P19 ⭐ нодовый конструктор
```

**Минимально полезный релиз (MVP) = P0 + P1 + P2 + P4.** Дальше — по одной фиче.
P10, P11, P12 и P13 — только когда всё остальное работает и живёт своей жизнью.

**P15 и P16 — самые дешёвые из оставшихся** (≈2.5 дня каждая) и самые полезные сразу: P15 снимает зависимость от «включи Secure DNS в браузере», P16 превращает машину в точку раздачи и переиспользуется в P11 целиком.
**P15 и P16 идут после P14** и не конфликтуют с ним: служба их не касается, DNS и SOCKS живут в пользовательской сессии.

**P17 → P18 → P19 — одна линия, и порядок в ней не случаен.** Сначала конфиг
становится своим (P17): его можно создать, сохранить и передать. Потом его
начинает создавать программа (P18), но всё ещё в тот же формат. И только потом
появляется визуальный редактор (P19), который редактирует **ту же модель**, а не
заводит вторую. Если сделать редактор первым, он придумает свой формат, и P17/P18
придётся переделывать под него.

**P14 — ближайшая из «звёздочек».** Она не требует ни нового движка, ни новых
платформ: только P/Invoke к SCM и четыре кнопки. И она закрывает реальную дыру —
сейчас обход умирает вместе с окном. Оценка ~1 неделя.

**P13 идёт раньше P12, если браться.** Причина простая: `Core` без Windows-зависимостей
и CLI — это 5–7 дней работы, которая полезна уже на Windows (тестируемость, скриптуемость,
«как Zapret Manager»), и она же фундамент и для Linux, и для Android. Android без этого
всё равно упрётся в «ядро срослось с WinForms».
