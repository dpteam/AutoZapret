feat: download the engine from inside the app, and check encodings everywhere

Two things the user asked for, and both were real holes.

1. "Who is going to fetch the engine?" The portable package shipped WITH
   engine\, but the self-contained artifact did not, and the only way to
   get an engine was tools\fetch-engine.ps1 - which needs git, PowerShell
   execution policy, and a console. For a product whose whole point is a
   GUI for people who do not want that, it was the worst possible first
   run experience.

   EngineInstaller downloads two zip archives over HTTPS, unpacks what is
   needed and places it in engine\. No git, no console. The new user sees
   one button on the home screen and a progress line next to it.

   Sources are the same as in fetch-engine.ps1: Flowseal main for bin+lists,
   SnAnVl zapret2 for winws2.exe and lua ONLY. Mixing the two bin sets is
   forbidden (AGENTS.md) - Flowseal winws.exe is 203 776 bytes, the bundle
   one is 223 232, and nobody tested the combination.

   Guards, because a broken engine is worse than no engine:
   - ZIP signature check: an HTML error page is detected and rejected
   - size sanity on the archive and on winws.exe afterwards
   - zip-slip: entries with ".." or a path outside the target are skipped,
     and the same IsInsideDirectory() helper is what the selftest asserts
   - v2 failure does not fail the whole install; v1 alone is usable

   Verified live: --install-engine fetched both engines, wrote version.txt
   1.10.4, EngineLocator reports v1 and v2 available.

2. tools\ was not in the artifacts at all, while the README referred to
   tools\fetch-engine.ps1. Now publish.cmd, build.yml and release.yml copy
   tools\ next to the exe.

3. Encoding checks (tools\check-encoding.ps1, wired into ci-test.ps1).
   This is the "half one way, half the other" class of bug: invisible in a
   diff, loud at runtime, and impossible to diagnose from the error text.

   The checker found real defects immediately:
   - all three .cmd files were LF-only; cmd needs CRLF for if/else blocks
   - publish.cmd had Cyrillic, which cmd prints as OEM garbage
   - publish.cmd had a stray ")" inside an echo INSIDE an if block. cmd
     parses the whole block even when the branch is not taken, so the ")"
     closed it early and the script died mid-way with exit code 255 and a
     message that decoded to nonsense. That was the "successful build with
     an error" from the user's screenshot - not robocopy at all, though
     robocopy's exit code was a separate real bug.

   The checker now enforces: UTF-8 validity everywhere, BOM on .ps1 with
   Cyrillic, ASCII-only and CRLF-only .cmd, no parentheses in echo, and no
   mixed line endings in any file.

   publish.cmd went from exit 255 half-way through to exit 0 with the full
   layout: exe + WebView2Loader.dll + engine\ + assets\ + tools\.
