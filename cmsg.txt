feat(P5): verify SHA-256 of the update archive against release checksums

SelfUpdater downloaded AutoZapret-portable.zip and then ran it through a
replacement script - with no integrity check at all. One spoofed response
was enough to execute someone else's code with our privileges. AGENTS.md
required this check; it simply was not implemented.

Now: fetch checksums.txt from the same release tag, find the entry for
AutoZapret-portable.zip, compare before extracting. release.yml already
publishes checksums.txt, so the two halves finally meet.

The important decision is failing CLOSED. A soft mode ('no hash, carry
on') defeats the entire point: an attacker just withholds checksums.txt
and the check silently disappears. So a missing file, an unparsable
file, an empty file, or a missing entry all abort the update with a
reason the user can read.

Parser handles the two formats found in the wild:
  sha256sum: '<64 hex>  <name>' (also the '*' binary marker)
  BSD:       'SHA256 (<name>) = <64 hex>'
Name matching strips any directory part ('.\x.zip', 'dist/x.zip') and
ignores case, because release assets are named inconsistently. Duplicate
entries keep the FIRST value - overwriting with the second would let a
tampered trailing line win.

HTML instead of checksums throws rather than parsing to zero entries:
that is what a redirect to a login page looks like, and 'zero entries'
would otherwise be reported as a generic parse failure.

CLI: --sha256 <file> prints hash, size and, if checksums.txt sits next to
it, the comparison verdict (exit 0 match, 2 mismatch).
selftest: 26 checks - known SHA-256 vectors for '' and 'abc', file hash,
both formats, path stripping, comments, duplicates, HTML rejection, the
missing-entry refusal, and URL consistency with PortableZipName.

Verified by hand: a real exe with a correct checksums.txt returns 0, a
falsified hash returns 2 and prints both values.
